# AWS経験者のためのAzure実践入門【公開サービス編】
## 〜スケーラビリティと公開セキュリティを備えたSaaSインフラを構築する〜

# 0. 本書の位置づけと設計方針

## 前提と読み方(基礎編との接続)

- 前提:【共通基礎編】で構築したミニランディングゾーン(dev/prodサブスクリプション、RBAC、ポリシー、vnet-dev/prod、Log Analyticsワークスペース、Bicepの型)
- **序章に以下を収録(基礎編未読者・経験者向けの緩和策)**:
  1. **「基礎編の到達状態」1枚構成図** — 本書はこの状態から開始する
  2. **最低限の用語ミニ対訳表** — サブスクリプション/RG/NSG/Entra ID/マネージドID など15語程度
  3. **スキップ判定チェックリスト** — 「この10項目が全部わかるなら基礎編を飛ばして本書から読んでよい」(例:リソースグループとタグの違いを説明できる、マネージドIDでキーレス接続を構成できる、NSGとSGの差を言える…)
  4. 基礎編相当を自力で用意する読者向けの最小構築手順(Bicep一式のダウンロード先)

## 題材システム

架空のイベント・チケット販売SaaS「TicketWave(仮称)」

- 主催者がイベントを公開し、購入者が在庫の限られたチケットを買う。**在庫・スパイク・決済**の三点が本書の技術的背骨
- 構成:Web API(コンテナ)+ RDB + キャッシュ + オブジェクトストレージ + 非同期処理 + 利用者ログイン
- AWSでの相当構成(読者の既存イメージ):ALB/CloudFront + ECS Fargate + RDS + ElastiCache + S3 + SQS/SNS + Cognito
- ゴール:dev環境で一式を動かし、prod環境を閉域化・冗長化・監視・自動デプロイまで仕上げる
- **題材の最小仕様(データモデル・API・章対応表)は `02_service_system.md` を単一情報源とする**。各章のハンズオンはそこで定義した要素だけを前提にする

## 各章の共通フォーマット(シリーズ共通)

全章、次の5つの定型ラベルの順で書きます(`shared/style-guide.md`・`CLAUDE.md` に準拠。基礎編と同じ体裁で、シリーズを通して同じ順序で読める)。

1. **概要** — Azureにおける位置づけと設計思想
2. **AWSとの対応と相違** — 対応サービス、似ている点、決定的に違う点
3. **全体構成に組み込む** — 前章までの構成にこの章の要素をどう足すか(Before/After図)
4. **設計のポイント** — スケーラビリティ・セキュリティ・コストのチェックリスト
5. **構築手順** — 手を動かす最小手順(ハンズオン)

- 各節の見出しは「**定型ラベル ── その章固有の一言**」の形にします。本書の主眼であるスケーラビリティ観点は「設計のポイント」に内包します。
- **例外:第18章(総仕上げ)**は新しいリソースを足さないため、③のラベルを **「全体構成を確認する」** に振り替えます(基礎編第7章と同じ扱い)。

## 学習の流れ(4フェーズ・全18章)

| フェーズ | 章 | 到達点(読者ができるようになること) |
|---|---|---|
| Phase 1: 動くものを作る | 1〜8章 | devにTicketWave一式。ブラウザから触れ、ログインして購入できる |
| Phase 2: 公開品質に上げる | 9〜11章 | 独自ドメイン・WAF・閉域backendの本番グレード公開 |
| Phase 3: 運用できるようにする | 12〜14章 | 監視・セキュリティ運用・自動デプロイ |
| Phase 4: 完成させる | 15〜18章 | コード化・DR・コスト最適・Well-Architectedレビュー |

> 本書は「公開サービス編」ですが、公開は最終盤ではなく **第2章で早くも「動いた」を体験**します。Container Apps は既定で公開URLを持つため、以降の章は「公開する」ことではなく「**公開を本番品質へ引き上げる**」ことに費やされます。各章の到達点は「サービスを足す」ではなく「**これができるようになる**」で示します。

- 執筆前の**要検証ホットスポット見積もり**(章別の陳腐化リスクと handson-logs 取得順)は `verification-hotspots-02.md` を参照。とくに第6章 Redis・第8章 External ID・第10章 API Management は製品情報が流動的なので、本文断定前に公式Docと GA 状況を確認します。

# Phase 1: 動くものを作る — devにTicketWave一式を載せる

## 第1章 コンピューティングの選択肢 — VM / App Service / Functions / コンテナの全体地図

- **到達点**:題材の要件から「なぜContainer Appsか」を自分で選べる。検証VMにBastion経由で一度だけ触れる
- **概要**:Azureのコンピューティング全体像。VM・VMSS・Bastion(IaaS)、App Service・Functions(PaaS)、Container Apps・AKS(コンテナ)の守備範囲と選定基準
- **AWSとの対応と相違**:EC2/ASG/Session Manager、Beanstalk/App Runner/Lambda、ECS/EKSとの対応マップ。「ECS相当の独自オーケストレータがなく、Container Apps か AKS の二択になる」構図、「AzureではApp Serviceが主役級」という文化差
- **全体構成に組み込む**:題材SaaSの要件(販売開始スパイク・コンテナ資産・運用体制)で選定プロセスを実演し、**Container Appsを主軸に採用**(App Service案・AKS案の棄却理由も明示)。検証用VM+BastionでIaaSの型も一度だけ体験(パブリックIPを付けない習慣づけ)
- **設計のポイント**:選定デシジョンツリー、Spot/サイズ体系の読み方
- **構築手順**:Bastion経由VM接続(体験)→以降のコンテナ路線の宣言
- ※App Serviceの詳説は社内DX編が主担当(参照を明示)。AKS詳細は本シリーズ外(別編推奨)

## 第2章 コンテナ実践 — ACR と Container Apps

- **到達点**:**販売APIがContainer Appsの既定URLで動き、ブラウザから叩ける**(本書最初の「動いた」)
- **概要**:Azure Container Registry、Container Apps(リビジョン、スケールルール、KEDA/Dapr内蔵)
- **AWSとの対応と相違**:ECR/ECS Fargate/App Runnerとの対応。タスク定義⇔リビジョン、サービス⇔アプリの読み替え表
- **全体構成に組み込む**:題材APIをコンテナ化し、ACR+Container Appsでdevに配置。**マネージドIDでACRからpull**(基礎編で学んだキーレス原則の最初の実践)
- **設計のポイント**:スケールルール(HTTP同時実行数/キュー長)、最小レプリカ0のコスト効果と冷起動、イメージスキャン
- **構築手順**:build→push→デプロイ→スケールルールで負荷時の自動増減を観測

## 第3章 ストレージアカウント — S3と似て非なるもの

- **到達点**:電子チケット・イベント画像をBlobに保存し、アプリから読み書きできる
- **概要**:ストレージアカウントという「箱」、Blob/File/Queue/Table、アクセス層、SAS、冗長オプション(LRS/ZRS/GRS)
- **AWSとの対応と相違**:Blob⇔S3、Files⇔EFS/FSx、Queue⇔簡易SQS。最大の違い=バケット単位のS3に対し、冗長性・ネットワーク設定が「アカウント単位」になること。署名付きURL⇔SAS
- **全体構成に組み込む**:電子チケット(QRコード画像/PDF)・イベント画像の保存先としてBlobを追加。マネージドID+RBACでアクセスし、アクセスキーを無効化
- **設計のポイント**:冗長オプション選定、パブリックアクセス禁止の徹底、ライフサイクル管理
- **構築手順**:Blob作成→アプリからアップロード→SAS発行体験

## 第4章 データベース — Azure SQL / PostgreSQL Flexible Server / Cosmos DB

- **到達点**:イベント・チケット種別・注文をPostgreSQLに永続化し、アプリから接続できる
- **概要**:Azure SQL Database(DTU/vCore・サーバーレス・自動チューニング)、PostgreSQL/MySQL Flexible Server、Cosmos DBの位置づけと概説
- **AWSとの対応と相違**:RDS/Auroraとの対応、「Azure SQLはRDSよりマネージド度が高い」。Cosmos DB⇔DynamoDBは対応表+概説に留め、パーティション設計等の深掘りはアプリアーキテクチャ編第6章へ(責務分離の明示)
- **全体構成に組み込む**:PostgreSQL Flexible ServerをVNet統合でdevに追加。接続文字列は次々章Key Vaultへの伏線
- **設計のポイント**:vCore/DTUの選び方、自動バックアップとPITR、Entra ID認証でのDB接続
- **構築手順**:構築→アプリから接続→PITRの動作確認

## 第5章 Key Vault — シークレットと鍵の一元管理

- **到達点**:**コードにも環境変数にも生シークレットがない**状態を完成させる
- **概要**:シークレット/キー/証明書、RBACモード、ソフトデリートとパージ保護
- **AWSとの対応と相違**:Secrets Manager+KMS+ACMを1つに束ねた存在。ローテーション設計の差
- **全体構成に組み込む**:DB接続情報・決済ゲートウェイのキー等をKey Vaultへ移し、Container AppsからマネージドIDで参照
- **設計のポイント**:RBACモード推奨、監査ログ、prodのパージ保護必須
- **構築手順**:シークレット登録→アプリの参照切替→ローテーション演習

## 第6章 キャッシュ — Azure Cache for Redis

- **到達点**:残席を高速表示し、**同時購入が殺到してもオーバーセルしない**
- **概要**:Azure Cache for Redis の階層(Basic/Standard/Premium/Enterprise)と新世代 Azure Managed Redis、VNet統合/Private Endpoint対応、クラスタリング
- **AWSとの対応と相違**:ElastiCache(Redis OSS/Valkey)との対応。Valkeyフォーク以降のエンジン事情とAzure側の現状(執筆時に最新確認の注記)、ノード/シャード概念の読み替え
- **全体構成に組み込む**:人気イベント一覧・残席数のキャッシュ先としてdevに追加。マネージドID(Entra ID認証)接続。**在庫カウンタと分散ロックでオーバーセルを防ぐ**最小実装
- **設計のポイント**:SKU選定とメモリ見積もり、エビクションポリシー、可用性(レプリカ)
- **構築手順**:構築→cache-asideの最小実装→残席の在庫確保をロックで直列化→ヒットの確認
- ※分散ロックの厳密な設計論・無効化戦略の深掘りはアプリアーキテクチャ編第5章へ

## 第7章 メッセージングとイベント — Service Bus / Event Grid / Event Hubs

- **到達点**:決済を同期APIから剥がして非同期確定にし、入場スキャンをストリームで流せる
- **概要**:Service Bus(キュー/トピック、DLQ、セッション)、Event Grid(イベントルーティング)、Event Hubs(ストリーム)の三兄弟の使い分け、Storage Queue(第3章)との棲み分け
- **AWSとの対応と相違**:SQS/SNS/EventBridge/Kinesisとの対応表(本書で最も需要の高い対比の一つ)。標準/FIFOキュー⇔Service Busの機能対応
- **全体構成に組み込む**:決済確定処理を Service Busキュー+**Functionsコンシューマ**に移行(Functionsの実践はここで担当)。購入完了通知を Event Grid、入場ゲートのスキャンログを Event Hubs で流す。いずれもマネージドIDで送受信
- **設計のポイント**:三兄弟+Storage Queueの選定デシジョンツリー、DLQ監視、少なくとも1回配信と冪等コンシューマの前提
- **構築手順**:キュー構築→Functionsトリガーで決済確定→電子チケット発行→DLQへの落ち方を観察
- ※Outbox・サーガ等の設計パターンはアプリアーキテクチャ編第8章へ

## 第8章 Entra External ID — サービス利用者の認証基盤

- **到達点**:**購入者がサインアップ/ログインして自分の注文を扱える**(Phase 1完成)
- **概要**:External ID(旧Azure AD B2C)の位置づけ、**社員用テナントとは別物である**こと(最重要)、サインアップ/サインインフロー、ソーシャルログイン、MFA、カスタムブランディング、MAU課金
- **AWSとの対応と相違**:Cognito User Poolsとの対応。ユーザープール⇔External IDテナント、Hosted UI⇔ブランディング、料金体系の違い。※B2C→External IDの移行期のため情報流動性に注意(執筆時最新確認の注記)
- **全体構成に組み込む**:題材SaaSに購入者ログインを追加。APIはトークン検証まで実装
- **設計のポイント**:**トークンを受け取るまでが本書(インフラ)の範囲、その先の認可ロジックはアプリアーキテクチャ編第3章の範囲**という線引きを明示
- **構築手順**:テナント作成→サインアップフロー構成→ソーシャルログイン→APIのトークン検証
- **Phase 1完了時点の構成図**:dev一式(Container Apps + PostgreSQL + Redis + Blob + Service Bus + Key Vault + External ID)

# Phase 2: 公開品質に上げる — 本番の入口と閉域化

## 第9章 負荷分散と配信 — Front Door / Application Gateway / Load Balancer

- **到達点**:独自ドメイン+WAF付きの本番入口ができ、販売開始スパイクをさばける
- **概要**:Load Balancer(L4)、Application Gateway(L7+WAF)、Front Door(グローバルCDN+WAF)、Traffic Manager、Azure DNS
- **AWSとの対応と相違**:NLB/ALB/CloudFront/Global Accelerator/Route 53との対応。「Front Door ≒ CloudFront+Global Accelerator+WAF」という束ね方、選定デシジョンツリー
- **全体構成に組み込む**:prod用構成を構築開始。Front Door(WAF付き)→Container Appsの入口、カスタムドメイン+マネージド証明書。External IDとの関係(認証はアプリ層で行い、Front DoorはWAF・配信に徹する構成)を整理
- **設計のポイント**:WAFポリシー(OWASP/ボット対策)、TLS終端位置、DDoS Protection、販売開始スパイクへの備え
- **構築手順**:Front Door構成→WAFルールのブロック確認

## 第10章 API Management — APIの公開と統制

- **到達点**:主催者向けのパートナーAPIを公開し、レート制限とキーで守れる
- **概要**:API Management の製品/サブスクリプションキー/ポリシー(レート制限・変換・検証)、開発者ポータル、SKU(Consumption〜Premium)
- **AWSとの対応と相違**:API Gateway(usage plan/APIキー/ステージ)との対応。「製品」という束ね概念、Consumption⇔HTTP API の対応感覚
- **全体構成に組み込む**:公開APIの入口としてAPIMを配置(Front Doorとの役割分担図)。レート制限・サブスクリプションキー発行までを構築(スパイク対策の第2層)
- **設計のポイント**:APIMを入れる/入れない判断基準(コストと規模)、認証の二重化を避ける構成
- **構築手順**:API取り込み→レート制限ポリシー→キー発行と疎通
- ※プラン別レート制限などビジネスロジックとしての活用はアプリアーキテクチャ編第4章へ

## 第11章 Private Endpoint — 本番のネットワーク閉域化

- **到達点**:prodのbackendをすべて閉域化し、パブリック経路を遮断できる
- **概要**:Private Endpoint / Private Link、サービスエンドポイントとの違い、プライベートDNSゾーン
- **AWSとの対応と相違**:VPC Interface/Gateway Endpointとの対応。**AzureのPaaSは既定でパブリックのため、閉域化の重要度がAWS以上に高い**(基礎編第4章で張った伏線の回収。Azure案件のセキュリティ指摘最頻出ポイント)
- **全体構成に組み込む**:prodのDB・Redis・Blob・Key Vault・ACR・Service Busをすべて Private Endpoint化し、パブリックアクセス遮断。プライベートDNSゾーンを整理
- **設計のポイント**:DNSゾーンの集約管理、devはどこまでやるかの費用対効果
- **構築手順**:Blobを閉域化→パブリック経路遮断の確認→DNS解決の観察

# Phase 3: 運用できるようにする — 観測・防御・自動化

## 第12章 監視の実践 — Application Insights とアラート設計

- **到達点**:障害をトレースで追え、在庫枯渇や決済失敗率でアラートが鳴る
- **概要**:Application Insights(分散トレース・可用性テスト)、診断設定の総点検、アラートとアクショングループ、KQL実践
- **AWSとの対応と相違**:CloudWatch Alarms+X-Rayとの対応。基礎編第5章で作ったワークスペースに全prodリソースを載せる「集約文化」の完成形
- **全体構成に組み込む**:APIにApp Insights組み込み、SLO的アラート(可用性・レイテンシ・エラー率)、Service Bus DLQ滞留アラート
- **設計のポイント**:サンプリングとコスト、アラート疲れを防ぐしきい値設計
- **構築手順**:障害を意図的に起こし、トレースで原因区間を特定→アラート発報
- ※アプリ側の構造化ログ・相関ID設計はアプリアーキテクチャ編第12章へ

## 第13章 セキュリティ運用 — Defender for Cloud と Sentinel

- **到達点**:セキュアスコアで設計の答え合わせをし、指摘を是正できる
- **概要**:Defender for Cloud(CSPM+ワークロード保護)、セキュアスコア、Sentinel(SIEM/SOAR)概要
- **AWSとの対応と相違**:Security Hub+GuardDuty+Inspector ≒ Defender for Cloud。Sentinel相当の統合SIEMはAWS標準にない構図
- **全体構成に組み込む**:prodにDefenderプランを有効化し、セキュアスコアの指摘に沿って是正(**これまでの全章の設計の答え合わせ**として機能する構成)
- **設計のポイント**:Defenderプランのコスト判断、Sentinel導入の要否基準
- **構築手順**:セキュアスコア確認→推奨事項を2〜3件是正

## 第14章 CI/CD — GitHub Actions で dev→prod パイプライン

- **到達点**:pushからdev自動デプロイ、承認を経てprodへ、を通しで回せる
- **概要**:GitHub ActionsとOIDC連携(フェデレーション資格情報)、環境と承認ゲート、Azure DevOpsの位置づけ
- **AWSとの対応と相違**:CodePipeline文化との違い(AzureはGitHub/Azure DevOps主流)、OIDC連携はAWSのGitHub OIDCと同じ発想
- **全体構成に組み込む**:push→dev自動デプロイ→承認→prodデプロイ。デプロイ用IDは最小権限+シークレットレス
- **設計のポイント**:ブランチ保護、環境承認、コンテナのリビジョン分割による安全なロールアウト
- **構築手順**:一連のパイプラインを構築し通しで体験

# Phase 4: 完成させる — 再現性・堅牢性・コスト

## 第15章 IaC本格化 — Bicepモジュールで全環境をコード化

- **到達点**:本書で作った全リソースを再現可能なコードにし、prodはパイプライン経由でのみ変更できる
- **概要**:モジュール分割、パラメータによるdev/prod差分表現、what-if運用、CI/CDへの組み込み(基礎編第6章の「型」からの本格化)
- **AWSとの対応と相違**:CFnネステッドスタック/CDK Constructとの対応
- **全体構成に組み込む**:本書で作った全リソースをモジュール化し、「prodはパイプライン経由でのみ変更可」の統制を確立。ポータルで作ったものをIaC化する現実的ワークフローも正面から扱う
- **設計のポイント**:モジュールの粒度、パラメータとバリアントの管理、what-ifの読み方
- **構築手順**:主要モジュール化→what-if→パイプラインからのデプロイ
