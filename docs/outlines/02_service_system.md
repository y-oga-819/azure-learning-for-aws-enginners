# 公開サービス編 題材システム仕様(最小・単一情報源)

本書【公開サービス編】の全章のハンズオンは、この 1 つの題材システムを一貫して育てます。各章はここで定義した要素だけを前提にし、本書独自の設定を勝手に足しません。用語・データモデル・API の面はこのファイルを単一情報源とします(アウトライン `02_service.md` と対で扱う設計書。凍結扱い)。

## 1. システム概要

- **仮称:TicketWave**(名称は仮。販売開始時に押し寄せるトラフィックの「波(wave)」を捌く、が主題)
- 架空の**イベント・チケット販売 SaaS**。主催者がイベントを公開し、購入者が席数・枚数の限られたチケットを買います。
- 一言でいうと:**「売り切れる在庫」を「一斉アクセスの中で」「お金を絡めて」捌く**システム。

### なぜこの題材か(在庫・スパイク・決済)

タスク管理のような CRUD 中心の題材と決定的に違うのは、次の 3 つを同時に扱う点です。これが本書と続巻【アプリケーションアーキテクチャ編】の技術的な背骨になります。

| 特性 | 何が起きるか | 引き出される設計 |
|---|---|---|
| **スパイク** | 販売開始の瞬間に負荷が跳ねる | オートスケール・CDN・レート制限が机上でなく必然になる |
| **在庫** | オーバーセル(売りすぎ)は許されない | 分散カウンタ・分散ロック・楽観排他が必要になる |
| **決済** | 外部決済は非同期・少なくとも 1 回・冪等 | メッセージング + 非同期コンシューマ、続巻でサーガ/Outbox |

## 2. 登場人物(最小 3 アクター)

| アクター | できること |
|---|---|
| 購入者(一般ユーザー) | イベント閲覧・チケット購入・電子チケット受け取り |
| 主催者 | イベント作成・チケット種別と在庫の設定・売上確認 |
| 入場スタッフ | 会場で QR コードをスキャンして入場確認 |

## 3. 中核ユースケース(全章で一貫させる 4 本)

1. 主催者がイベントとチケット種別(在庫数つき)を登録する。
2. 購入者がログインし、チケットを**枚数指定で購入**する(在庫を減らす。**オーバーセル禁止**)。
3. 決済は**非同期**で確定し、確定後に電子チケット(QR コード)を発行・通知する。
4. 当日、入場スタッフが QR コードをスキャンし、**入場ログがストリームで流れる**。

## 4. データモデル(最小エンティティ)

リレーショナル部分は PostgreSQL、在庫の即時性が要る部分は Redis に持たせる二層構成を前提とします。

| エンティティ | 主な属性 | 置き場所 |
|---|---|---|
| Organizer(主催者) | id、名前、プラン(続巻でテナント化の起点) | PostgreSQL |
| Event(イベント) | id、主催者 id、名前、説明、会場、開催日時、公開状態 | PostgreSQL |
| TicketType(チケット種別) | id、イベント id、名称、価格、**在庫総数** | PostgreSQL |
| Order(注文) | id、購入者 id、チケット種別 id、枚数、金額、状態(pending/paid/failed) | PostgreSQL |
| Ticket(電子チケット) | id、注文 id、QR トークン、入場状態 | PostgreSQL(QR 画像は Blob) |
| 在庫カウンタ | チケット種別ごとの残数 | Redis(PostgreSQL の在庫総数を単一の真実として、販売中の即時判定に使う) |

- QR コード画像・イベント告知画像・電子チケット PDF は **Blob** に保存します。
- 決済ゲートウェイのキー・DB 接続情報などのシークレットは **Key Vault** に置き、コードにも環境変数にも生のシークレットを置きません。

## 5. API の面(最小エンドポイント)

| メソッド | パス | 概要 | 主なアクター |
|---|---|---|---|
| GET | `/events` | 公開中イベント一覧(キャッシュ対象) | 購入者 |
| GET | `/events/{id}` | イベント詳細と残席数 | 購入者 |
| POST | `/orders` | 購入(在庫確保 → 注文 pending 作成) | 購入者 |
| POST | `/payments/webhook` | 決済ゲートウェイからの確定通知受信 | 外部(決済) |
| GET | `/orders/{id}/ticket` | 電子チケット取得 | 購入者 |
| POST | `/organizer/events` | イベント・チケット種別の登録 | 主催者 |
| POST | `/checkin/scan` | QR スキャンによる入場確認 | 入場スタッフ |

## 6. 各章がこの題材から自然に引き出される(章対応表)

| 章 | 題材上の要素 | 引き出される Azure |
|---|---|---|
| 第1章 | 急峻なスパイク・コンテナ資産・常時起動不要な処理あり | コンピューティング選定(Container Apps 主軸の根拠) |
| 第2章 | 販売 API 本体 | ACR + Container Apps(購入スパイクで自動スケール) |
| 第3章 | 電子チケット/QR コード・イベント画像 | ストレージアカウント(Blob) |
| 第4章 | イベント・在庫・注文・座席 | PostgreSQL Flexible Server |
| 第5章 | 決済ゲートウェイのキー・DB 接続情報 | Key Vault |
| 第6章 | **在庫カウンタ・待機列** | **Redis(分散ロックでオーバーセル防止)** ← 目玉 |
| 第7章 | **決済確定・購入完了通知・入場スキャンログ** | **Service Bus + Functions / Event Grid / Event Hubs** ← 三兄弟が全部要る |
| 第8章 | 購入者のログイン | Entra External ID |
| 第9章 | 販売開始スパイクの公開入口 | Front Door + WAF |
| 第10章 | 主催者向けパートナー API 公開 | API Management(レート制限=第 2 の防波堤) |
| 第11章 | 本番リソースの閉域化 | Private Endpoint |
| 第12章 | 販売開始の負荷可視化・在庫枯渇/決済失敗率 | Application Insights とアラート |
| 第13章 | 決済を扱う公開サービスの防御 | Defender for Cloud / Sentinel |
| 第14章 | 販売開始前の安全なロールアウト | GitHub Actions で dev→prod |
| 第15章 | 全体のコード化 | Bicep モジュール |
| 第16章 | 販売はビジネスクリティカル | 可用性・DR・バックアップ・コスト |
| 第17章 | 完成構成と続巻への接続 | Well-Architected レビュー |

とくに**第6章(Redis)と第7章(メッセージング)が無理なく主役になる**のがこの題材の価値です。CRUD 中心の題材だと「一応入れる」感が出ますが、チケット販売では**入れないと在庫と決済が破綻する**ため必然性が段違いです。

## 7. 続巻【アプリケーションアーキテクチャ編】への伏線

本書はインフラ構築に徹し、以下は「課題として置くだけ」で深掘りしません(続巻の担当)。

- **オーバーセル防止の厳密な設計論**(分散ロック/楽観排他/在庫の整合)→ 続巻のキャッシュ・状態の章
- **決済のサーガ/Outbox パターン**(注文・在庫・決済の結果整合)→ 続巻のイベント駆動の章
- **マルチテナント化**:本書の Organizer を、続巻で**マルチ主催者(テナント)**へ本格化する。料金プラン(Free/Standard/Enterprise)は主催者プランとして展開する。
- **残席数のリアルタイム反映**(購入画面への即時反映)→ 続巻のリアルタイムの章

## 8. スコープ外(意図的に切る)

- 実際の決済処理・返金・会計ロジック。決済ゲートウェイは**外部サービス**とし、本書は Webhook 受信までを担当します。
- 座席表の描画・座席指定 UI などのフロントエンド作り込み。
- チケットの転売対策・本人確認などの業務要件(題材を複雑にしすぎないため割愛)。
